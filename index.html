01 — The Migration Engine

From Repository to Recommendation

Four stages, two live today and two in active development — we'd rather tell you than fake it.

Scan Repository

Upload a .zip of your codebase. Extraction runs through path-traversal and archive-bomb protections — validated against a real zip-slip payload — before anything touches the workspace, then you get a source tree view of what was scanned.

Crypto Findings

Python is analyzed via its AST; Java via the JCA's getInstance() call pattern, which also catches Bouncy Castle. Findings cover RSA, ECDSA, ECDH, DSA, DH, X25519/X448, Ed25519/448, AES, SHA-256 and above, MD5/SHA-1, and embedded PEM keys and certificates.

Recommendation Engine

Each finding is read for how the key is actually used, not just its algorithm name — key establishment maps to ML-KEM-768 (FIPS 203), signatures map to ML-DSA-65 (FIPS 204).

Generate & Verify Migration

Guided code migration and post-migration verification, built on the same findings and recommendations.

02 — Security & Compliance

We Hold Ourselves to the Same Standard

The same rigor we bring to your migration is built into how Quantera itself runs.

Post-Quantum Encryption at Rest

Every document Quantera stores is protected the way we recommend to you: a fresh AES-256-GCM key per file, wrapped with ML-KEM-768, with metadata signed by ML-DSA-65.

Role-Based Access Control

Three enforced roles — user, admin, compliance — with server-side authorization on every privileged action and automatic lockout after repeated failed logins.

Local-First Processing

Local inference and local storage by default. If a request is ever routed to an external model, it passes through a data-loss-prevention gate first.

Tamper-Evident Audit Trail

Every scan and every request is written to a hash-chained log that can be independently verified end to end — not just a timestamped table.
