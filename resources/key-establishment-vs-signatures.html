Key Establishment vs. Digital Signatures

Why "replace RSA" isn't a complete migration plan.

Same algorithm, two different jobs

RSA shows up in source code doing at least two structurally different things. Sometimes it's protecting a symmetric key — wrapping an AES key so it can be safely shared or stored, a job called key establishment. Sometimes it's proving a piece of data came from a specific party and hasn't been altered — a digital signature. Elliptic-curve cryptography splits the same way: ECDH for key agreement, ECDSA for signatures.

A scanner that reports "RSA-2048 detected" doesn't tell you which job that instance is doing. That distinction isn't a technicality — it determines what the finding should actually be replaced with.

Why the replacement isn't the same algorithm

NIST's first two finalized post-quantum standards map cleanly onto these two jobs, and only onto one each:

  • ML-KEM (FIPS 203) is a key-encapsulation mechanism — built for key establishment. It replaces what RSA-OAEP and ECDH were doing.
  • ML-DSA (FIPS 204) is a digital signature algorithm — built for signing and verifying. It replaces what RSA-PSS/PKCS#1 signatures and ECDSA were doing.

Neither algorithm does the other's job. ML-KEM doesn't produce signatures; ML-DSA doesn't encapsulate a key. A migration recipe that maps "RSA" to a single replacement, without first determining which of these two roles that RSA instance plays, will get roughly half of its recommendations wrong.

Where this actually shows up in code

A single service can easily contain both patterns a few files apart: an RSA key wrapping an AES data-encryption key in one class, and RSA-signed transaction receipts in another. They look similar in a flat scan result — "RSA-2048" twice — and need entirely different migrations. Telling them apart requires reading how the key is used: is it feeding a Cipher operation that wraps another key, or a Signature operation that signs a payload? That's a call-graph and context question, not something visible from the algorithm name alone.

What this means for a migration tool

A recommendation engine that's actually useful has to classify usage before it recommends anything — key establishment gets mapped to ML-KEM, signatures get mapped to ML-DSA, and it has to get that classification right at the level of the specific call site, not the file or the service.
